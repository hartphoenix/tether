# Tether Fly setup

Open **Folio → Settings → Set up Tether Fly**. Setup fills the same tab; **← Settings** returns without losing answers. Start with this computer, choose Paseo, cmux, Wave or Browser, and paste the generated prompt into an agent session on the named computer. Keep Settings open for approvals and progress. Setting up Fly does not expose your hub to the internet.

After verifying this computer, use **Connect a machine or browser** for each additional computer. When ready, choose **All my computers are connected** to select the hub from the connected computers. The current hub starts selected and appears in bold; you can keep it or move the library to another available computer. **Hub controls → Choose hub** is available later.

The hub holds the library; file machines hold Markdown. The hub accesses its own files directly. Other file machines use a connector; Paseo also needs a separately enrolled agent/plugin client on its daemon machine. cmux supports background reader delivery; Wave provides document links to open. Browser-only access installs no connector. Each browser signs in separately at the hub’s HTTPS origin, using a passkey or configured fallback password. Browser sessions last 30 days; agent and connector credentials last 90 days.

The reader’s theme picker includes **Desktop** and **Mobile**. The choice stays in that browser’s storage for the current Tether origin, independently of shared themes or other browsers. Until you choose, touch-first input, a mobile browser hint, or a mobile user-agent selects Mobile; otherwise Desktop is used. Resizing never changes the selected interface.

## Agent procedure

These are agent operations; the owner should only need the Settings and approval pages. Use the exact reviewed source commit named in the prompt, Bun 1.3.9, root `bun.lock`, and `integrations/paseo/package-lock.json`. Never claim native Paseo compatibility from a successful build alone. The desktop embedding remains experimental.

1. Inspect the selected machine, existing installation, Paseo daemon, configuration and supervision. Preserve existing profiles and private connection files. Run `bun install --frozen-lockfile` in the checkout; for Paseo, run `npm ci` inside `integrations/paseo`. Run `bun scripts/check-fly-install.ts --role service|connector|browser --directory <private-directory> --origin <https-origin>`, adding `--paseo <executable>` for Paseo. A connector needs no Chromium; the hub needs Playwright’s sandboxed Chromium. Distinguish an inspection restriction from a stopped service. Use [shared-profile prerequisites](shared-profile.md).
2. On the existing hub, configure its final HTTPS origin before enrolling anyone. Local-owner control accepts `tether shared manage configure --input '{"origin":"https://host.example","port":8420}'`; it starts only a loopback application listener. Ordinary HTTPS proxies must forward that listener with the public Host preserved. Keep daemon control private. For a Tailscale pilot, choose a dedicated port at the machine’s stable `.ts.net` hostname and run `bun scripts/configure-fly-network.ts --attempt <id>` on the hub. It uses the owner’s saved internet-access answer, refuses to overwrite another application’s route, and reports external approval separately. Resume the same command after approval. Check access from the intended viewing machine; Funnel additionally needs a browser outside the VPN.
3. Establish or recover the owner passkey through **local Settings → Set up or recover owner passkey**. The final HTTPS page receives its short-lived enrollment code directly from the local page. Finish there and return to Settings. Password fallback can be created in local Settings or a verified hub session; changing it ends other browser sessions. Nothing in an agent prompt authorizes password creation or passkey recovery remotely.
4. Contact the attempt with `tether remote setup --state <private-file> --origin <https-origin> --attempt <id> --name <agent-name> --wait 300`. The owner approves that named reporting request in Settings. Keep the private state file and rerun the same command after interruption. Report bounded observations with `tether remote report --state <private-file> --phase <phase> --message <observation>`. Phases are `awaiting prerequisites`, `awaiting owner`, `awaiting approval`, `installed`, and `needs repair`. Reports are unverified and cannot grant library access or certify completion.
5. Browser-only setup ends at sign-in and a verified document workflow. When the selected file machine is the hub itself, preserve its local profile and machine ID, apply the chosen path-copy preference in Settings, and skip connector pairing and installation: a hub cannot connect to itself. For another file machine, request a connector using `remote pair --kind connector --origin <origin> --name <client-name> --machine-name <display-name> --qualify-paths yes|no --connection <private-file>`. When reconnecting, add `--machine <retained-id>` from the hub’s machine inventory. Pairing requires an enrolled owner; approval uses the owner’s passkey. Run `remote complete --connection <same-file> --wait 300` while the owner approves in the browser. Rerun against that same file after a lost response. Expired requests renew through `remote pair`; an accepted credential is reused and a revoked credential retains its machine ID. Never delete pending files to retry.
6. On those other file machines, run `bun scripts/install-headless.ts --role connector --profile <profile> --directory <installation-directory> --connection <private-file> --supervise yes`. The installer repairs its own assets and starts launchd or the user’s systemd service; it refuses a mismatched installation. On a new hub, use role `service` and its existing library configuration. On a running hub, preserve its existing supervisor. Confirm connection and actual file access separately.
7. For Paseo, enroll an **agent** client, explicitly associated through `remote pair --kind agent --machine <retained-id>`, and complete its approval. Install the directory plugin with `paseo plugin install <checkout>/integrations/paseo` on the selected daemon machine, then `paseo plugin reload tether`. Set its Tether executable to that checkout’s launcher and **Shared connection** to the private agent credential file. Inspect the remote daemon’s plugin list and logs, not the Mac daemon’s. Honor Paseo’s plugin trust approval. Do not restart active agents or create replacement workspaces.
8. For Paseo on a separate file machine, bind CLI calls for existing sessions with `tether remote bind --connection <agent-file> --receiver <plugin-client-id>` in the intended unused client profile. It refuses to replace an existing local library. Every call in that profile now uses the hub. On the hub itself, keep its existing local profile instead of binding a remote profile over it; add `--connection <agent-file> --receiver <plugin-client-id>` to shared CLI calls, including the examples below. For existing Paseo sessions, pass `--workspace <actual-paseo-workspace-id>` when announcing; new sessions receive the workspace environment automatically. Use `open id:<document-id> --host paseo --workspace <id>` or `recents add <path> --machine <id> --host paseo --workspace <id>`. Missing routing returns an undelivered result and safe browser URL. Never infer the focused workspace. Make the matching [review skill](agent-setup.md) available through the supported agent integration; persistent instruction changes require their usual approval.
9. For cmux, enroll an agent client for the retained machine ID as in step 7, then run `tether remote receive --connection <private-file> --host cmux` in the receiving terminal. Route announcements through its connection with `--connection <agent-file> --receiver <client-id>` (including on the hub, without rebinding its local profile); verify background delivery in that captured workspace. For Wave, open the returned document links: background placement is currently unsupported. In either app, check browser sign-in, reading, editing, comments and appearance; confirm these checks in Settings. Paseo additionally requires the actual native sidebar, sign-in and return, workspace notice, pin/archive/restore and tab restoration. Run read → comment → agent reply/edit → refresh and stale-write rejection on disposable Markdown. For remote file machines, observe connector loss and recovery. Record the source SHA, plugin SHA, app/daemon versions, installed paths, and evidence in the setup report; keep passwords, cookies, bearer credentials and reporting capabilities out of output.

## Management and recovery

Settings lists file machines separately from browser sessions and unassociated clients. Assign legacy agent clients explicitly before revoking a machine. The confirmation lists every affected client; a concurrent association change requires a fresh confirmation. Revocation preserves machine IDs, documents and reviews. Renaming is case-insensitively unique; plain paths are the default, and qualified copies use the file machine’s current name on every viewer.

**Disable all Tether Fly connections** revokes all clients and pending approvals, then rejects shared access. Local Settings remains available. Re-enabling requires fresh browser sign-in and client pairing. Network loss alone never revokes access. A saved attempt survives hub restart; its reporting capability expires after 30 minutes and the attempt after one day. Changing answers invalidates the old reporting approval. When offline, Settings reports waiting for contact; it cannot diagnose the agent’s network remotely.

## Relocate the hub

Choosing a different connected computer as the hub produces an agent handoff. Preserve the selected destination’s existing machine ID as well as the source’s; document associations must survive the move. The agent must retain the old hub’s file-machine identity because Markdown stays there. Stop its supervisor before cutover. On the source, `tether relocate prepare --output <private-backup-directory> --destination <machine> --attempt <setup-id> --confirm` fences startup, stops writes and makes a resumable backup. Copy it privately and use `tether restore --source <backup> --directory <new-config-directory>`. Verify the backup checksums, document/review identities and required file-machine paths before release; the destination remains inactive.

Before release, `tether relocate rollback --confirm` permits restarting the source. To commit the cutover, run `tether relocate release --output <private-receipt-file> --confirm` on the stopped source, transfer the receipt privately, and run `tether relocate activate --receipt <private-receipt-file> --confirm` on the stopped destination. The receipt never belongs in a prompt or log. Release is irreversible: keep the old authority fenced and repair the destination after any later failure. Repeating activation retains the destination’s identity.

Configure and verify the final HTTPS origin, recover its owner passkey if the origin changed, then re-pair retained file machines, including the former hub. Activation revokes copied client sessions; it does not forward credentials between origins. Start exactly one authority and verify existing document IDs and reviews before resuming edits. This workflow transfers private state, not arbitrary Markdown or the separate mobile pilot’s database; retain the pilot until shared-mobile parity and migration are explicitly verified.
