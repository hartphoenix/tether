# Tether platform research

Researched 2026-09-20. Official platform documentation and published audience studies; architecture checked against this checkout. These are documented capabilities and implementation inferences, not integrations tested in running clients.

Related: [[chat-surface-research-2026-09-20.md|A themed agent chat using existing subscriptions]].

**Recommendation:** make local VS Code the first audience pilot, build one reusable MCP facade for desktop agents, and test a shared MCP App reader in Claude Desktop before committing to broad chat integration. Keep the existing browser reader as the comparison baseline. Public evidence supports this ordering provisionally; it does not establish which interface Tether’s actual users prefer.

Three separate questions govern portability: where the reader appears, how the agent calls Tether, and where the authoritative document lives. A macOS wrapper addresses windowing and startup; it does not provide integration inside another app or connect a cloud agent to local files.

| Stack Overflow 2025: VS Code leads IDE use; Markdown leads admiration among documentation/collaboration tools. IDE question: 26,143 responses; documentation question: 30,065. | A credible VS Code recruitment pool, not evidence of demand for Tether. Admiration measures continued-use preference. The 49,009-person survey was self-selected, largely through Stack Overflow channels, fielded May 29–June 23. [Results](https://survey.stackoverflow.co/2025/technology), [methodology](https://survey.stackoverflow.co/2025/methodology) |

No reviewed study cross-tabulates **persistent Markdown use × passage-review need × agent surface × operating system**. Product user counts, extension installs, and website visits cannot supply that missing intersection. “Vibecoder” is also an unreliable recruitment filter: ask what people actually create and review. Writers, researchers, educators, and product planners who already use Markdown are plausible adjacent segments, but demand from those groups remains a hypothesis.

MCP tools, MCP Apps, and installation packages are distinct. Tools expose operations; MCP Apps add sandboxed HTML communicating through a host bridge; packages install/configure capabilities. OpenAI now documents a shared plugin directory, but explicitly excludes plugin support in the Codex IDE extension; configure MCP there directly. Do not promise that installing one package activates every surface. [Plugin availability](https://learn.chatgpt.com/docs/plugins)

Claude’s remote custom connectors currently cover Free through Enterprise, with one connector on Free and organization controls for managed accounts. Anthropic’s private MCP tunnels are an Enterprise research preview requiring access, unsuitable as a normal consumer installation path. OpenAI developer-mode access depends on account/workspace policy. Exact entitlement and embedded-UI behavior need a fresh-account check before advertising support. [Claude connectors](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp), [Claude tunnels](https://claude.com/docs/connectors/mcp-tunnels/overview), [OpenAI testing](https://developers.openai.com/plugins/deploy/connect-chatgpt)

**Core reuse is credible, but the present host interface is insufficient by itself.** [HostAdapter](../src/hosts/host-adapter.ts) controls opening and host actions. The [reader](../src/web/app.ts) uses same-origin HTTP and daemon-owned body saves; [Folio](../src/web/folio-page.ts) uses HTTP/SSE and browser storage. The [server](../src/server/server.ts) enforces scoped sessions and origin checks. These are concrete coupling points to adapt, not reasons to rewrite the document/review model.

The smallest useful architecture change is three explicit boundaries:

1. **Agent operations:** a stdio MCP facade over the existing daemon client, preserving bounded pending/thread/context/diff reads, revisions, operation receipts, and acknowledgements. Keep tool definitions stable and usable without UI; do not implement a second mutation engine.
2. **Reader transport and host actions:** retain HTTP for existing hosts; add VS Code message passing and MCP Apps bridge implementations. Reuse Milkdown, themes, anchors, and thread UI. Persist drafts and document identity outside disposable chat views; Folio must remain recoverable across conversations. Do not replace origin checks with permissive CORS.
3. **Document ownership:** daemon disk saves remain authoritative in existing hosts. A VS Code custom text editor must use `TextDocument`/`WorkspaceEdit` for dirty buffers, undo, save, and backup. The daemon keeps private reviews; handling anchors on unsaved text needs an explicit revision policy. A first reader/review pilot can require saved files and disable body editing. [VS Code contract](https://code.visualstudio.com/api/extension-guides/custom-editors)

For MCP Apps, package the UI as a resource and use the standard bridge first; add host-specific features only after capability detection. A chat result can offer an expanded reader, but is not automatically a persistent editor tab or application-wide Folio. Reopening, links, file selection, keyboard focus, and draft recovery are acceptance tests. [MCP Apps](https://modelcontextprotocol.io/extensions/apps/overview), [ChatGPT UI](https://developers.openai.com/plugins/build/chatgpt-ui)

Start VS Code support with local macOS workspaces. Remote SSH, containers, and Codespaces place files/runtime elsewhere: webview `localhost` may mean the wrong machine. Use webview → extension → daemon routing. Plain `vscode.dev` cannot spawn Bun; supporting it requires a backend or larger runtime change. [Remote extensions](https://code.visualstudio.com/api/advanced-topics/remote-extensions), [web extensions](https://code.visualstudio.com/api/extension-guides/web-extensions)

| Standalone option | Practical consequence |
| --- | --- |
| Existing browser / installed web app | Lowest additional shell work. Safari already supports Add to Dock on macOS Sonoma+. An app-like window still cannot restart a stopped daemon without a launcher/bridge. [Apple](https://support.apple.com/en-gb/104996) |
| Tauri or a small WKWebView shell | Reuses the OS webview on macOS; Tauri can bundle the existing backend as a sidecar. Adds native packaging, lifecycle, update, and WebKit validation work. [Webviews](https://v2.tauri.app/reference/webview-versions/), [sidecars](https://v2.tauri.app/develop/sidecar/) |
| Electron | Reuses web code and provides consistent Chromium rendering, while bundling Chromium/Node alongside Tether’s backend. Easy initial wrapping does not remove distribution or lifecycle work. [Electron](https://www.electronjs.org/docs/latest) |

Prefer the existing browser for the pilot; consider a native shell only if installation, startup, or window management emerges as a repeated obstacle. Bundling less runtime does not prove lower memory consumption: compare actual idle CPU, total process memory, cold-open latency, and several-document use. VS Code warns that retaining hidden webviews costs memory; restore state instead of keeping every reader alive. [Webview lifecycle](https://code.visualstudio.com/api/extension-guides/webview)

The next development decision should follow a bounded comparison:

1. Prove one shared MCP facade against the local daemon. In Claude Desktop, test real-file selection, an embedded reader, a private comment/reply exchange, and reopening after restart. Test ChatGPT’s local UI combination separately. This establishes portability without a cloud service.
2. Build the saved-file VS Code reader/review pilot with Folio. Compare it against the existing browser reader before investing in full editor ownership or remote workspaces.
3. Recruit 12 existing document reviewers: four VS Code agent users, four desktop-chat users, four browser-chat users; include professional and nonprofessional builders and record OS, file location, and actual Markdown use. Observe their own document: open → annotate → agent response/revision → revisit. Record unaided completion, installation time, copying/context switching, and voluntary reuse over seven days. For people using multiple surfaces, alternate presentation order.

Treat this sample as directional usability evidence, not market sizing. Advance the adapter whose users complete real review loops and return; reconsider an embedded implementation if the companion reader performs equally well. If browser users chiefly work with cloud artifacts rather than local files, test explicit import/export before proposing synchronization. Authentication, relays, cloud storage, and conflict handling would then be a separate product commitment, not a minimal adapter.

No integrations or audience interviews were performed in this research pass; no platform latency/memory measurements are claimed. The product plan is unchanged.
