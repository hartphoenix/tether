# cleanup proposal

## Proposal: private conversations and simpler document handling

*Revised after review · 2026-09-06 · Proposal only; no application changes or data conversion performed.*

Store annotations in one private local SQLite database. Keep annotation text out of ordinary Markdown files so copying, sharing, or committing a document does not accidentally share its conversations. Treat documents and their discussions as temporary working material: prioritize a small, understandable system over exhaustive identity tracking.

The design decisions are settled: use canonical file paths to identify conversations, keep Markdown free of Tether footers, and name the working list **Tether Folio**. The comparison below records the trade-offs considered. No human-gated design decisions remain.

**Two storage designs: the actual trade-offs**

Both designs store all conversations in the same private database. The difference is how an opened file finds its conversation.

| Trade-off | A. Path-based identity; no footer | B. Opaque UUID in an HTML-comment footer |
| --- | --- | --- |
| Mechanism | Canonical absolute path maps to a private document record. | A comment such as `<!-- tether:id=… -->` maps to a private document record. |
| Simplicity | Smallest implementation. No file metadata writer or relocation detector. | Small identifier parser/writer; no elaborate external tracking. |
| Document cleanliness | Opening, commenting, and clearing never change Markdown bytes or modification time. | First attachment of an ID changes the file. Later comments only change the database. The footer remains visible in source and Git. |
| Ordinary move or rename | New path starts without the old conversation. Use a simple Locate file action on the old record if the conversation matters. | The same ID reconnects to the local conversation wherever the file is moved, provided the footer survives. |
| Copies and templates | Different paths naturally start separate conversations. | Copies carry the same ID and therefore refer to the same conversation in that local store. Starting a separate conversation requires assigning a new ID. |
| Same path reused | A replacement file inherits that path's association. Start fresh clears the association when wanted. | A replacement with a different or absent ID starts separately. |
| Git branches/worktrees | Branches at one path share the association; another worktree has different paths. | A committed ID travels between branches, clones, and worktrees; locally they can point to the same conversation. |
| Sharing privacy | No Tether data travels in the file. | Only the ID travels. It contains no comments, but links copies by identifier. It does not carry the database or expose it remotely. |
| Another machine | Copying Markdown does not bring its annotations. | Copying Markdown still does not bring its annotations: the other machine needs the database or an annotation package. |
| Read-only documents | Can be annotated privately without writing the file. | Cannot attach a new ID. A path fallback or refusal to attach is needed; the fallback introduces a second mechanism. |
| Accepted failure | Some renamed or reused files need manual reconnection/reset. | Copied IDs share a conversation until separated; removed footers break the association. |

**Selected: A, path-based identity**, because these conversations are ephemeral and an occasional lost association is acceptable. This recommendation no longer depends on bookmarks, filesystem IDs, content matching, directory scans, or a relocation engine. A single Locate file action updates the stored path. If the destination already has a conversation, report that conflict; do not merge it automatically.

Design B was considered and rejected. Do not implement UUID footers, identity modes, external tracking, or legacy-ledger support.

**Private store and profiles**

Use one normal application data store and one daemon for the user. Store document records, current locations, conversations/events, acknowledgement cursors, active/archive membership, settings, and resumable reader state. SQLite is the authoritative store, not a backup. It suits local application data and transactional updates. [SQLite appropriate uses](https://www.sqlite.org/whentouse.html).

Today a “profile” is a namespace selecting separate runtime/config directories: daemon discovery, control credentials, Recents, theme preferences, and host bridge records. `preview` is hardcoded in the Wave launchers and used by the documented commands; an unconfigured CLI defaults to `default`. They do not currently separate embedded annotations, because those live in the documents. [Configuration](../src/server/config.ts#L40), [Wave launcher](../src/hosts/wave-launchers.ts#L42).

Their practical value is development/test isolation. There is no current product need for Hart to manage multiple profiles. Consolidate normal launches onto one store, preserving existing Recents and theme preferences after inspecting both locations. Keep explicit temporary directory overrides for tests and isolated development; remove profile selection from normal usage. Do not delete or merge current configuration as part of this proposal review.

Keep only the revision/context data needed for anchors and safe saves; do not build an unlimited document-version archive. Maintain separate body and conversation revisions. Annotation writes must not rewrite the document, with no footer exception.

**Naming the current Recents page**

The page is a clearable working list, not a host workspace or a filesystem manager. Avoid Workspace and Desk.

**Tether Folio** is selected. Its two views are **Active** and **Archive**. Do not use Workspace or Desk, which overlap host terminology. No named workspaces or project-management hierarchy.

Show title, compact directory/repository, and attention state. Include enough path to distinguish duplicate filenames. Offer these sorts:

- Recently opened, the default.
- Document modified, from filesystem modification time.
- Conversation activity, separate from document edits.
- Added to Folio.
- File created, where available; do not silently substitute another timestamp.
- Name.

Offer directory/repository grouping and filtering, plus needs-attention and missing-file filters. Work from known entries and local metadata; no general document crawler. Pinned entries survive Clear unpinned.

**Clearing, archiving, and deletion**

| Action | Effect |
| --- | --- |
| Clear from Folio | Remove from Active and place in Archive under the chosen retention policy. Leave the Markdown file alone. |
| Clear unpinned | Apply the same action to the unpinned selection. |
| Reopen from Archive | Return to Active and cancel its expiry. |
| Delete conversation | Delete its private review data after one confirmation. Leave the file alone. |
| Start fresh | Discard the old conversation after confirmation and begin separately at the same path. |
| Move file to Trash | Separate filesystem action. Never implied by clearing or expiry. |

Archive retention defaults to **30 days from clearing**. Settings offer a number of days, **Keep forever**, or **Delete immediately**. Reopening cancels expiry; clearing again starts a new period. Expiry removes that archived entry and its associated conversation/recovery data, never the Markdown file. Active entries do not expire. Check overdue archive entries on startup and periodically while running.

Changing the retention setting applies to Archive using each entry's original clearing time. Confirm once if that change will immediately delete existing entries. In Delete immediately mode, clearing is a deletion and uses a single confirmation rather than promising an unavailable Undo. Normal archiving can offer Undo. No recurring privacy lectures or backup warnings.

**Privacy, access, and backups**

The user and their trusted local agent can access the user's annotation store. There is no per-document ownership or permission hierarchy within that store. The relevant privacy protection is keeping annotations out of files shared through ordinary OS and Git operations.

Keep existing loopback authentication and browser session scoping so unrelated web pages cannot operate the local service. That transport boundary does not imply that Hart needs additional permission to read their own annotations. Do not place credentials in Markdown, exported packages, or view URLs.

Store the database outside document folders and repositories, with user-only permissions. The user manages backups using their own tools. Do not add a backup scheduler, backup-management UI, deletion tombstone system, or restore warnings. The live database is primary application data. Document its location and, if needed, a concise consistent-copy procedure; SQLite provides an API for coherent copies of a live database. [SQLite backup guidance](https://www.sqlite.org/backup.html).

**Export with annotations**

Ordinary documents are copied and moved using the OS. There is no separate Export Markdown feature.

Provide **Export with annotations** per document and for a batch selection, with a matching **Import annotations** operation. Use one versioned archive containing each current Markdown body and its unresolved conversations in their current displayed form, including their original comments, replies, authors, and anchors. Do not include raw event history, deleted text, drafts, acknowledgement cursors, or absolute local paths. This is one simple package, not a menu of historical export modes.

An imported package supplies portable conversations; it does not depend on access to the exporting machine's private store. Let the user choose where to place the Markdown files and associate the imported conversations with those files by their canonical file paths. Validate package structure and prevent archive paths from escaping the chosen directory. Do not overwrite existing files silently. This package import is new functionality, distinct from unsupported legacy-ledger import.

**Lifecycle: agreed direction**

An **Open Tether** launcher starts or reconnects to the service and opens/focuses Folio. Opening a document or running an agent command also starts/reuses the service. Closing Folio does not stop open readers. Keep Restart service in diagnostics and provide Quit Tether; normal use should require neither terminal commands nor an agent to cycle the daemon.

Keep conversations and reader restoration state on disk, independent of service sessions. A restart should reconnect readers with fresh scoped sessions and restore their saved position. Preserve drafts before a controlled restart; if a recovered draft's base file changed, show the conflict rather than overwriting the file.

Cold restoration needs a launcher/user-service component outside the daemon: a dead daemon cannot serve its old URL. Audit Wave/cmux support before promising automatic in-place restoration. The minimum is one Open Tether action that restores the working set. Host credentials and launch tickets remain outside persistent view descriptors.

**Implementation scope and order**

There is no shipped migration flow, legacy-ledger import, backwards-compatible annotation CLI, or dual storage system. Existing annotated documents can be left behind. If a handful later prove worth keeping, handle them as a one-off agent task. That is not a requirement for the new application. This review continues using the existing ledger until the redesign is built; this document edit does not remove it.

1. Use the settled design: canonical file paths, no footer, and Tether Folio.
2. Build the private store and annotation repository with one normal application data location. Consolidate existing non-annotation settings deliberately; preserve test isolation through temporary directories.
3. Implement private comments/replies, Archive retention, and export/import packages. Test the accepted path-based identity trade-offs rather than trying to solve every filesystem edge case.
4. Add Folio organization and automatic service startup/recovery.
5. Rebuild the small review CLI parsing/dispatch layer against the new contract. Reuse the authenticated transport, daemon lifecycle, core review semantics, and useful tests; remove legacy annotation compatibility rather than rewriting sound unrelated code.

The new CLI should address the audit's concrete issues: strict arguments, compact reads, safe acknowledgement cursors, retry-safe mutations, and clear errors. No requirement to preserve the old annotation response schema. Resolve/acknowledge remain distinct: answering a question does not automatically remove it from the user's attention.

Body saves still need revision checks and protection against external edits. Saving a changed passage and inserting an anchored comment are separate operations; report partial completion if the body saved but the comment failed. Moving annotations into SQLite removes whole-file writes for replies, but does not make ordinary Markdown saves immune to concurrent editors.

Acceptance: no annotation text appears in ordinary Markdown; identity behavior matches the path-based column above; clearing never deletes a file; Archive expires after the configured period; reopening cancels expiry; package export/import round-trips current unresolved conversations; restart preserves committed review state and saved drafts; the CLI cannot acknowledge unseen events through an ambiguous mutation sequence; no old-ledger compatibility is required.

**Settled decisions**

- Canonical file paths identify conversations; no watermark or external identity tracking. Locate file reconnects a moved document when needed.
- Tether Folio is the working list, with Active and Archive views.
- Archive retention defaults to 30 days, configurable as days, Keep forever, or Delete immediately.
- One normal application store/daemon; retain temporary-directory isolation for tests and preserve existing settings during consolidation.
- User-managed backups; no migration product or old-annotation CLI compatibility.
- Export with annotations and matching import, available per document and in batches; no plain Markdown export.
- Automatic service startup; reader lifetime is independent of the Folio view.
- Storage first, then rebuild review CLI parsing/dispatch while reusing sound transport, lifecycle, review semantics, and tests.

No human-gated design decisions remain. Host restoration capabilities and existing configuration contents still need inspection during implementation; those are engineering tasks, not pending product choices.
